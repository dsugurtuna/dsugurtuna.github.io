Beyond code: what most people actually need from AI

Five-sixths of conversational AI outputs sit outside software engineering—in decisions that have no compiler to catch quiet mistakes.

Ugur Tuna · 22 November 2026 · 3 minute read

Follow product announcements or leaderboards and AI looks built mainly for software engineers. Coding is genuinely productive, and I write software myself. Yet inside most organisations, high-stakes work rarely touches a code editor. Teams spend their days shaping strategy, digesting technical evidence, reviewing contracts, and weighing operational risk in plain English.

Why labs spotlight software engineering

As Mark Sullivan noted in Fast Company, three incentives keep AI labs focused on code [1]. First, software budgets buy developer speed immediately. Second, code offers clean training feedback: a script compiles and passes tests, or it fails, whereas a policy memo has no unit test. Third, better coding agents speed up lab research itself. Those are good reasons for labs to benchmark code—not for enterprises to ignore non-coding work.

What organisational usage actually shows

Empirical usage records tell a wider story. In Anthropic’s June 2026 Cadences report, code and scripts accounted for only about one-sixth of outputs across conversational Claude and workspace tools [2]. Roughly a third were explanations and guidance, and another third were written deliverables such as reports, memos, and plans. Nearly a quarter of users surveyed (23%) were managers, and 68% said AI helped them learn faster. On ChatGPT, OpenAI’s October 2026 Signals v3.0 report tracked 165 work activities across nearly a hundred countries, showing adoption spreading across non-technical roles [4].

Non-coding value comes from structured dialogue, not single prompts. In Cadences, drafting an article took a median of thirteen turns against one prompt in a coding agent, and judgement-heavy roles sustained sessions 1.5 times longer [2]. In Anthropic’s January 2026 Economic Primitives study across 117 countries and 50 U.S. states, answer quality tracked prompt depth at 0.93 correlation. Multi-turn iteration stretched reliable task scope from 3.5 hours to roughly 19 hours [3].

Why non-coding workflows are harder to govern

Software teams have compilers, linters, type checks, and CI suites between a draft and production. Policy, legal, finance, and operational teams do not. When staff paste unredacted contracts or personal records into chat without structure, three governance gaps open immediately:

  • Unscreened data flows: confidential or personal data enters tools without zero-data-retention guarantees or DPIA screening.
  • Blurred decision authority: an exploratory draft acts as decision support without a named owner, independent assurer, or challenge route.
  • Unchecked fluency: confident prose omits an exception or misreads a clause because no automated test catches prose errors.

Proportionate governance in plain records

Governing non-coding AI well means applying software discipline without burying light use cases under thirty-page forms. In ai-assurance-kit, each use case sits in a schema-validated YAML record (abridged excerpt below) stating what data it touches, whether it drafts or supports decisions, and who owns vs assures it:

id: contract-policy-first-pass-review
title: "Contract & policy first-pass review"
status: in_test
accountability:
  business_owner: { role: "Legal Operations Lead" }
  assurer: { role: "Information Governance Lead" }
data:
  personal_data: false       # synthetic/redacted docs only
actions:
  mode: drafts               # never writes or sends
reliance:
  decision_role: decision_support
controls:
  - { id: C1, status: in_place, description: "Human verification before reliance" }
  - { id: C2, status: in_place, description: "Zero-training retention boundary" }

Keep coding assistants moving fast. Give non-coding workflows—where five-sixths of everyday knowledge work already sits—the same clear boundaries, human challenge, and verifiable assurance records.
